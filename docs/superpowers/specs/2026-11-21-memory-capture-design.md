# Memory capture from a session transcript: design

Status: the owner agreed to this design on 2026-11-21 and ruled C11 to C18 on 2026-11-22 while marking the trial, which passed its gate (step L3 of [the learning loop study](../../studies/2026-11-21-memory-learning-loop.md); stage 9 and decision D20 of [the memory plugin design](2026-11-17-memory-plugin-design.md)). Phase A is planned in [the trial plan](../plans/2026-11-21-memory-capture-trial.md); phase B is built only if the trial passes.

C28 to C38 (stage B3) were written on 2026-11-22 from the owner's choices of that day (C28, C32, C38) and approved by the owner on that day; the rows say which parts were the author's proposal. C39 was added the same day from research the owner asked for, and is the author's ruling on the method.

## Goal

Lessons, pitfalls and decisions of a session reach the project's memory even when the main agent did not record them, without adding wrong or duplicate records and without the main session waiting.

## Decisions

| # | Decision | Reason |
|---|---|---|
| C1 | A candidate is kept only when it is tied to one signal: `owner_correction`, `failed_then_passed` (a check or command that failed and later passed), `verified_review_finding`, `plan_changed_by_review`, `delegation_failed`, `rework`, `repeated_tool_error`, `decision_with_reason` | A model that criticises itself with no outside signal does not improve (study, E1) |
| C2 | Each candidate carries a quote of its evidence, and code drops the candidate unless that quote occurs in one line of the extract it was given; for the two owner signals that line must be the owner's own (a subagent's report is a different line kind) | Stored experiences propagate their errors (E9); the check is mechanical, not a second opinion of the same model |
| C3 | The process reads the transcript, never the compaction summary | Notes written from a summary carry more errors (E3) |
| C4 | The model gets no Bash and no web: it reads the extract and writes one JSON file inside a work folder; code validates and writes | As `mem-settle` does; a background model cannot write on its own |
| C5 | An unconfirmed captured record is written in the project scope; kinds `lesson`, `pitfall`, `decision`; at most 5 candidates per run | A wrong record must not reach every project before someone confirmed it; a cap keeps the review queue short |
| C6 | A captured record has origin `transcript` and is shown as `from transcript, unconfirmed` until it is corroborated (C11; `mem confirm` records a corroboration, and a second sighting counts as one); it is valid for 30 days | "Provisional" stays implicit in words agents already meet (`web, unconfirmed`, `mem confirm`); no new status, so no query that filters by status changes; an unconfirmed record expires by itself |
| C7 | The claims of the project's active memories are given to the model as "already recorded" | The main agent records too; an identical claim is already refused at writing |
| C8 | Haiku first; Sonnet only if the trial keeps too few | Cost; the trial decides |
| C9 | Phase A is offline: `mem-capture` writes candidates to a file and never to the store | Stage 9's adoption check comes before any hook |
| C10 | Each candidate has a `reach`: `project` (this codebase) or `general` (how the agent plans, delegates, uses skills and plugins, verifies, reads the owner's intent). A `general` record is marked for promotion, and moves to the global scope (`mem promote`) once it is corroborated as a general lesson under C12, not on a confirmation inside the one project where it was seen | The owner's goal is meta-learning (2026-11-21): a lesson about method must reach every project, not stay where it happened; the project scope is only where it waits |
| C11 | What the owner says, and a friction with the owner, are evidence and not truth. A record drawn from one comment or one friction is worded as what happened ("the owner rejected X, saying Y"), stays unconfirmed, and counts as established only when it is corroborated: the same lesson is seen again in another session, or independent evidence shows it (the owner said it and it then happened, a check confirms it). For an `owner_correction` the candidate also considers the other reading: the owner may have misunderstood, and the lesson is then to explain better or in a form adapted to the owner | The owner's ruling of 2026-11-22: the owner can be wrong, and a single friction does not say who misread whom |
| C12 | Corroboration is kept per scope. A `general` lesson seen in one project is established for that project at most, and stays unconfirmed as a general one until it is seen in a second project; the more a rule restricts the agent or the owner, the more sightings it needs | The owner's ruling of 2026-11-22: a rule that one project needed may not apply to the others |
| C13 | A claim states how often the thing was seen and under which condition ("refused on three merges in this repository", not "is always refused"), and reads as guidance the agent may set aside with a reason. A sighting that goes the other way is recorded as an exception, not as a refutation, so the rule can move to a middle point or become stricter | The owner's ruling of 2026-11-22: some frictions do not occur every time; a rigid rule cannot evolve |
| C14 | When a candidate is very doubtful or would cost much if wrong, the agent may ask the owner. The answer is one more piece of evidence that tilts the balance, as feedback or a preference, not proof (C11) | The owner's ruling of 2026-11-22 |
| C15 | The wording of a record carries its standing, beyond any tag: how sure it is, whether it may be temporary, which conditions are unknown, and how much it matters to follow it ("seen once; may only hold while X", "has held in three projects"). The sightings a lesson needs grow with what it costs if wrong: a grave or restrictive rule needs many, a mild and general one may need none | The owner's ruling of 2026-11-22: an agent reads prose, so prose is what tells it how firmly to apply a lesson, and a lesson that is not applied blindly can be refined |
| C16 | A lesson is told apart from a project record. A lesson must generalise beyond the event and read as a suggestion, a recommendation or, rarely, an instruction; the first two are the normal forms. A decision of the project, a fact of its documentation or a working note is not a lesson: it belongs in the project's own records (its decision records, its design, its memory as a `decision` or a `state`) and is not counted as learning, nor proposed as a general rule | The owner's ruling of 2026-11-22; in the trial three "lessons" were decisions already written in a project's design document |
| C17 | A lesson corroborated in several projects and situations enters a triage, not a silent promotion: someone decides what it becomes (a global record, a change to a rule such as an agent definition, a skill or a context file, a merge of its variants into one wording, or nothing more), and a rule change still needs the owner | The owner's ruling of 2026-11-22; in the trial one lesson, about a subagent's turn limit, appeared in 4 sessions of 3 projects as four separate candidates |
| C18 | An established rule lives in the memory store and is loaded from there and carries the weight its wording gives it (C13, C15), as if it were part of the instructions: the store travels to any model and any environment, an instruction file does not. Only when a rule kept there is still not followed does it move up a ladder, one step at a time and only as confidence grows: the memory store, then a skill or an agent definition, then the always-loaded instructions, which is the gravest step | The owner's ruling of 2026-11-22. Open: what loads established rules at session start without the cost measured for context files (study, E4): a short capped list, in the wording of C15 |
| C19 | The lesson records are the source; what loads at session start is a file generated from them under a token limit, in which each lesson gets space by its weight and its corroboration, and which can be regenerated at any time, more or less compressed, without losing anything | The owner's ruling of 2026-11-22: how strict the loaded rules are can then be tuned by regenerating, not by editing them |
| C20 | Each lesson has a weight, `light`, `medium` or `strong`, by how much it restricts and what it costs if wrong; the sightings it needs follow from it: light, one; medium, two, and two projects to count as general; strong, three across two projects, or the owner's confirmation (stage B1 counts sessions only: the two-project condition and the owner's confirmation come with stage B3). Starting values, to be adjusted from the data. A correction by the owner may be `light` like any other lesson (the owner, 2026-11-22): its weight follows what it restricts and what it costs if wrong, and a doubt about it is said in its wording. The capture model proposes a suggestion or a recommendation, never an instruction: that form is given only in triage | Agreed with the owner on 2026-11-22 |
| C21 | Learning is positive as well as corrective: a lesson may say that a way of working tended to give a better or cheaper result, with what made it work. Two signals carry it, `owner_approval` and `effective_practice`, each still tied to evidence in the session (the owner's words, or the visible result) | The owner's ruling of 2026-11-22: the aim is better performance and efficiency, not only fewer failures; the first eight signals were all failures |
| C22 | A background run reads forward in windows: each window holds at most 80,000 characters of extract, at most 3 windows per trigger, no new window once the trigger has written 5 new records, and the next trigger continues where this one stopped | Without the forward mode `extract` keeps the newest lines and drops the oldest when a stretch is long, and a compaction covers a long stretch; the cap keeps one trigger from flooding a project |
| C23 | The saved offset moves past a window when the window was full, or when a model session ran and ended without error. It stays when the window was too short and reached the end of the file, and when the window failed; a window that failed twice at one offset is skipped. A window whose candidates were all refused because `mem` could not run counts as failed | Short remainders accumulate until there is enough to read; a failed window is read again once and never blocks the rest of the session |
| C24 | A background run writes only into a project that already has its memory folder; elsewhere it skips with a reason in its log, never a failure | A background process must not create a folder in a repository the owner never set up for memory |
| C25 | One lock for all background captures of a data folder; a run waits up to 900 s for it. A run started at `PreCompact` first waits 300 s | The two triggers of one session can fire close together. The next context records the summary's "not yet recorded" items right after a compaction; the wait lets those writes reach the "already recorded" list (it does not help when the owner answers later) |
| C26 | Options `auto_capture` (boolean, off) and `auto_capture_budget` (USD per window, default 0.25). A failed run leaves one line in the session start text until `mem-capture ack` | As `auto_curation` and `auto_settle` |
| C27 | The offset and the sightings use one identity, the transcript file's stem | `run --write` already names the sighting `session <stem>`, so a session read twice adds no second sighting |
| C28 | Lessons are matched by meaning by one small-model session in the shape of `mem-settle` (C4): code writes the lessons as lines of id, claim and context; the model, with no Bash and no web, writes groups of ids that state one lesson and, for each group, one claim reworded with no name of a project, client, system, file or person; code accepts a group only when every id is known and no id sits in two groups. Rejected: matching by shared terms in code (free, but the trial showed it misses a reworded lesson and `mem search` with a whole claim returns unrelated notes); matching inside the capture session (it cannot regroup what is already written and its list grows with every project) | The owner's choice of 2026-11-22. On that day one lesson, a subagent that reaches its turn limit and returns no report, stood in three wordings: two global records and one project record |
| C29 | The pass reads the live records of origin `transcript` in every counted project and in the global scope. A project is counted when its registered folder exists and is not under the system's temporary folder. Inside one project it groups records of either reach; across projects, and against global records, only records of reach `general`. A global record of another origin, written by a session with `mem remember --global`, is not read and receives no sighting (author's proposal) | On 2026-11-22 the registry held 24 projects, 21 of them temporary copies left by trials: counted as projects they would corroborate a lesson falsely |
| C30 | A sighting on a global record names its session and an opaque key of its project (a hash of the project's path), so sessions and projects are counted on the record itself and no project name enters the global scope. A record can be written with several sightings at once. The form of the entry and its parsing are a change to the record format, named as such in the plan (author's proposal) | Counting through the registry alone breaks when a project record is retired or its folder moves; on 2026-11-22 `mem remember` took one source, so 15 recovered lessons kept their other sessions as prose that nothing counts |
| C31 | Thresholds for a global record, completing C12 and C20: `light` and `medium`, sightings in two projects; `strong`, three sessions across two projects. The standing of a global record of origin `transcript` follows this row, not the count of sessions alone, and the owner's confirmation establishes one of any weight and stands for its triage (author's proposal for `light` and `medium`). Below its threshold it is unconfirmed and valid for 30 days, as C6. Inside one project C20 is unchanged | C12 asks for a second project whatever the weight, so for a general lesson `light` and `medium` meet at two projects |
| C32 | When a group crosses its threshold the pass itself writes the global record, through `mem remember --global` so that the forbidden-term check stays the gate, marked as awaiting triage by a new field of the record (a change to the record format). A refused write, for a forbidden or a soft term, stays in the pass's log with its reason: code does not retry it with other words and the pass never approves a soft term. This row replaces the reading of C10 in which `mem promote` moves the record: that command stays the manual path. The project records stay, marked as promoted and linked to the global record, so the step can be undone | The owner's choice of 2026-11-22 (write, then review) over a queue that waits for a yes: learning must not stop when the owner does not review. Cost accepted: a lesson generalized wrongly may be read until it is reviewed |
| C33 | Triage is a category of `mem curate`, "general lesson awaiting triage", shown in the session start text as its own count, since the curation due counts only new and expired records. The owner or a main session accepts it (the mark is cleared), rewords it, or rejects it (the global record is retired and its project records are marked so the pass does not propose them again). The background curator does not accept one, as it does not confirm a transcript record. Turning a lesson into a rule (an agent definition, a skill, a context file) needs the owner (C17, C18) | The queue and its count already exist; a second place to review would be read less |
| C34 | Reworded duplicates inside one project are merged by the pass with the existing merge, which is logged and can be restored: the older record keeps its wording and receives the sightings of the other; each merge is listed in the run's log. Nothing is merged across scopes: a project record grouped with a global one adds its sightings to the global record and is marked and linked as in C32 (author's proposal) | Scope carried over from stage B2; one wording per lesson is what lets its sightings add up (C20) |
| C35 | The capture's "already recorded" list gives a handle to global records of origin `transcript`, and a `same_as` to one adds a sighting (C30) to that global record | Without it a lesson that is already global is shown as recorded, never proposed again, and so never gains a sighting |
| C36 | The pass, `mem-corroborate`, is started detached at the end of an automatic capture run that wrote at least one record or sighting, behind the option `auto_capture` and with the budget of C26; it starts after the capture has released its lock and has its own lock, status file, log of counts and failure line as C25 and C26 give the capture, one model session per run within that budget, and `run` and `--dry-run` by hand. No new hook and no new option (author's proposal) | New material is the only reason to match again; `SessionEnd` alone would miss it (C37) |
| C37 | A session left open is captured by a sweep: at session start, with `auto_capture` on, a detached run started by the existing session start hook reads the transcripts in the folder of the starting session's transcript that have lines after their saved offset and were not changed for 6 hours, at most 2 sessions per start and none older than 7 days, never the starting session's own; same lock, offsets and windows as C22 to C27 (author's proposal, the figures are starting values) | `SessionEnd` fires only when a session really ends (exit, `/clear`, a switch with `/resume`) and no event marks an idle one; on 2026-11-22 the previous session's process was still alive after 14 hours, so only a compaction would have captured it |
| C38 | A global record of origin `transcript` that is unconfirmed (C31) is in quarantine: searches, the session start text and the loaded rules of C19 do not show it; the capture's "already recorded" list, the pass and `mem curate` do. The pass gives every lesson of reach `general` such a global record at its first run, reworded as C28 asks, so a capture in any project can add a sighting to it (C35); this changes C32 in one point: the record is written before the threshold, and crossing the threshold (or the owner's confirmation) ends the quarantine and marks it as awaiting triage. The record keeps the date its quarantine ended. Quarantine ends on evidence that the lesson is true; whether it is useful can only be read afterwards, from sightings later than that date (the lesson was readable and the failure came back), and acting on that belongs to stage B4 | The owner's idea of 2026-11-22: a level of confidence below which a general lesson exists only to be confirmed. It lowers the cost accepted in C32, since a lesson nobody corroborated is not read. Cost: every general lesson is reworded and written to the global scope, not only those that cross a threshold |
| C39 | The pass proposes, then verifies (this completes C28, which named one session). A first session proposes the groups and the reworded claims. A second, independent session is shown each proposed group alone, the members' texts and the reworded claim, and answers per group, a one-sentence reason first: do the members state the same lesson; does the reworded claim keep the situation, the action and the reason and add nothing; is it a lesson about method that holds outside its project. Code applies only a group verified on all three; the rest is left as it was and not proposed again until a sighting changes it. The pass rewords a lesson once, when its global record is written, and never rewrites that record: later evidence only adds sightings. The gate of stage B3 records, for the first time here, how often the owner agrees with the applied groups and how often two runs of the pass agree with each other | Research of 2026-11-22 (the owner asked for the state of the art): in our own audit a Haiku judge agreed with itself on 6 of the verdicts it flagged in two passes, so one pass must not merge; the systems read (Mem0, A-MEM, LangMem, Zep, ACE) let a model decide after a cheap recall of candidates and publish no precision of that decision; memory rewritten at each consolidation loses content ("context collapse", omission as the most common error; authors' reports); small models judge better one case at a time and with a reason first; lessons about method transfer between domains and low-level traces transfer negatively (authors' report, abstract). No system read holds a new memory back until corroborated: C38 has no published precedent, so its effect is ours to measure. Sources: ADR 0023, Review of stage B3 |
| C40 | A reminder is a record that asks for a piece of work in a later session. It has a topic of at most 40 characters, a body that says the work and why, and optional conditions: a start date, a number of sessions to wait, an end date, a repetition (`30d` or `10s`). It lives in the project or the global scope, in a `reminders` folder beside the memories, with the same history and restore as a memory, and is never part of memory search, curation or the loaded rules | The owner's rulings R1 to R3 in [the B4 handoff](../plans/2026-11-22-memory-loaded-rules-and-reminders.md); the record shape follows Pro-Memory (an activation condition, once or recurring) |
| C41 | The data folder holds a count of sessions per project and a total. The session start hook raises both when a session starts, is cleared or is compacted; a resumed session raises nothing. A reminder stores the count at the moment it was armed, so "sessions since" is a subtraction. A project reminder uses its project's count, a global one the total. `mem` computes every date and count: the agent passes "in 3 sessions" or a date | The owner's ruling R5: a compaction means time or work has passed. Agents miscompute relative times |
| C42 | What loads at session start for reminders is one line of at most 300 characters, present only when one is due: how many are due, up to four topics each with the sessions since it was written, and how many wait. The full text is read with `mem reminders` | The owner's ruling R4: metadata only, kept very short |
| C43 | A reminder ends in one of four ways, each restorable: done, with a note of what was done (a recurring one arms itself again); closed, with a reason; put off, for a number of sessions or until a date; or its end date passes. One shown at five session starts with none of these is marked in the line as a question for the owner, keep or close. Nothing is removed in silence | The owner's ruling R2. A line shown at every start is learned to be ignored; an answer is not proof the work was done (Pro-Memory) |
| C44 | When a reminder is due, the agent decides whether to start the work or to ask the owner first, from what the work implies in cost, effort and risk. The reminder records an effort and a risk, `low`, `medium` or `high`, given when it is written, and `mem reminders` states the starting rule: low effort and low risk, do it after the current task and say so; otherwise propose it to the owner. A reminder run by a background agent with no other context is not built | The owner's ruling of 2026-11-22: it depends on the reminder and its implications; the background form is occasional and sensitive |
| C45 | The owner and the agent write reminders, the agent when it defers a finding or leaves an item open. No background pass writes one: a state that can be computed from the records is shown as a count line, as `Triage` is. A scope holds at most 10 live reminders | A stored copy of a computable state goes stale; the limit keeps the line short |
| C46 | The loaded rules of C19 are part of the session start text, built by code at each session start from the lesson records, and `mem rules` prints the same text; no model rewrites the list. A lesson loads when it is established and, for a global one, accepted at triage or confirmed by the owner. Each loads in a short form of at most 120 characters, written once when it is accepted and kept in its record, in this order: weight, then the projects and sessions that saw it, then its latest sighting | The owner's ruling of 2026-11-22: only established lessons load. Rewriting a whole list loses detail (ACE); earlier instructions are followed more (IFScale) |
| C47 | After the loaded rules, one line names what did not load: how many more recommendations there are and the topics they are about grouped with a count each ("12 more recommendations by topic: testing 5, process 4, shell 3 (mem rules --more <topic>)"), and `mem rules --more <topic>` prints only that group, so the agent can decide to read them, and when, at the cost of one line. It counts the lessons that qualify and did not fit. A lesson that awaits triage is not counted there, because the `Triage` line already announces it; `mem rules --more` lists it under that reason. A lesson with no short form yet is counted nowhere at session start. A lesson in quarantine is never counted or named there (C38 stands): it is shown only to the passes that look for evidence or similar lessons, as the corroboration pass does. Each lesson carries a topic for this line | The owner's rulings of 2026-11-22: the line, grouped by category with its numbers at the end so the rest is loaded when the agent finds it useful (a section that condenses the other rules with a model was the other option, not taken: it would load text nobody read, C54), and that quarantine is what keeps a lesson out of it; an agent that analyses lessons is the one to be told of them |
| C48 | Starting limits: at most 6 loaded rules and 900 characters of rule lines, and 200 characters for the line that follows them. The rest of the session start text keeps its own limit of 1500 characters, applied without the rules, so the project's memory rows give way before any rule. Failure lines, `Curation due` and `Triage` are never dropped | A row can be found by search; a rule that did not load cannot act. The real session start text had a median of 644 characters over 63 session starts in the owner's hook log on 2026-11-22, so six rules roughly double it: more would be the noise the owner fears. Context files raised cost by about 20% with no gain (study, E4) |
| C49 | A sighting of a lesson later than its `released` date counts as "loaded and it still happened". At two such sightings the lesson returns to triage with that reason: reword it, move it up the ladder of C18, or drop it. Exceptions (C13) are counted too, and when they reach the confirming sightings the lesson returns to triage as "may not hold". Nothing is dropped without the owner | ExpeL and ACE count against a lesson; here the owner decides, as in C33 |
| C50 | B4 is built in two releases: reminders with the session count first, then the loaded rules with C47 and C49. Each records what it showed and what followed (a reminder's showings before it was done, closed or put off; a rule's sightings after it loaded). Choosing rules by the task at each prompt is not built: revisit it if the second measure shows a fixed list is not followed | The owner's ruling of 2026-11-22. No outside measure of reminders or loaded rules acted on was found |
| C51 | Reminders (C40 to C45) are parked: built and reviewed on the branch `idea/memory-reminders`, not integrated. B4 is the loaded rules alone (C46 to C49). Work that should recur, a periodic refactoring or assessment, is kept as a lesson the agent learns, writes down and checks by itself whether it should be done, so it loads with the rules and needs no second mechanism | The owner's ruling of 2026-11-22. In one run with a real model a due reminder shown at session start was not acted on; reminders overlap with lessons; their noise (shown again after each compaction, written freely by the agent, global ones in every project, ended files never removed) outweighed a usefulness not shown. The branch's plan file records the state and what to change if it is taken up again |
| C52 | A lesson's topic and its short form are written by the small model when the lesson is generalized or first established, with no review by the owner before they load. The owner is asked only about what is grave or very doubtful: a lesson of weight `strong` waits at triage before it loads, and so does one the verifying session doubted; a `light` or `medium` lesson loads once it is established and is listed for review afterwards. This amends C33 and C46, where every released global lesson waited for triage | The owner's ruling of 2026-11-22: the suggestions reviewed so far were good, so it should go by itself. The owner confirmed on 2026-11-22 that `strong` is the measure of "grave" and that `light` and `medium` skip the wait. Built after the first release (C54) |
| C53 | In one measurement, short rules in the session start text were followed when they bore on the task. Measured on 2026-11-22 with a real model, one small task, three runs a condition: with no rules, none of three checkable practices was followed (0 of 3 runs each); with three rules in the session start text (printed by a throwaway hook, not by the plugin), all three were followed in 3 of 3 runs; with the same three among twelve unrelated rules, again 3 of 3, at about 7% more cost. So the list is worth building; what is not yet measured is a rule that conflicts with other instructions, a long session, and the owner's own always-loaded instructions beside it | The measurement in [the B4 handoff](../plans/2026-11-22-memory-loaded-rules-and-reminders.md#measurement-loaded-rules-are-followed-2026-11-22). It is the opposite of the reminders result (C51): a rule about the task in hand is followed, a request for other work is not |
| C54 | The first release of the loaded rules is the small one: a lesson loads only when it is established, has a short form, and is not turned off; a project lesson also needs two sessions or the owner's confirmation; every short form is proposed by the small model on request and read by the owner before it is applied; any one rule can be turned off without losing the lesson (`load: no`), and an edit of a claim removes its short form. The automatic writing of short forms and the lighter triage of C52 wait for a later plan, built on what this release shows | The pre-mortem of 2026-11-22: the first draft would have loaded lessons nobody had read (one project lesson seen once went against the owner's own instructions), the same eight in every project, with no way to turn one off, and a short form could drop the hedges of its claim. The owner's wariness of noise at session start (C51) |
| C55 | A lesson has one of three load states: it competes for a place among the loaded rules; it is index only, never among them and counted by topic in the line that follows, for the agent to fetch with `mem rules --more <topic>` when it finds the topic useful; or it is off and appears nowhere. A lesson that holds in any kind of work competes; one about a single kind of work (interface design, experiments, the web) is index only. The state is set when the owner reads the proposed short forms, in the same file | The owner's idea of 2026-11-22 (group the rest by category and let the agent load it when useful). In the first real batch thirteen of the fifteen lessons tied on every order key, so most of the six that loaded were the first by handle, and a lesson about one narrow kind of work would have loaded in every project |
| C56 | Text that the plugin loads for the model to read names the person as "the user", not "the owner": the standing words after a confirmed lesson read `(the user vouched for it)` (C57), and a short form says "the user". The project's own documents keep "owner" | The owner's ruling of 2026-11-22: "owner" does not convey the relation between the model and the person who works with it. The vocabulary rule of ADR 0007 is about the project's documents, not about text loaded into a session |
| C57 | The loaded block reads as lessons to apply with judgment, not as orders. Its header is `memory: lessons learned in earlier sessions. Apply them with judgment: follow one unless you have a reason not to, and mention a skipped one only when it matters to the user.`; a confirmed lesson ends with `(the user vouched for it)`; the index line says `N more lessons by topic: ... (mem rules --more <topic>, when a topic fits your task)`. The brief for a short form says what to drop when a claim does not fit (alternatives and detail first, never the hedge) and to say "the user". A rule is reworded in one command, claim and short form together. A plugin option, `loaded_rules`, switches the whole feature off | A prompt review before the release (2026-11-22): the first header told the model to follow, and to say so when it did not, above lines that are all hedged, which invites blind use or announcements; "confirmed by the user" can read as an order; the brief gave no order of loss, and failed twice on the two lessons with most hedges. ## Not in this design
